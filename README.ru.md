# ModxKit Testbench

> **Русский перевод.** Канонический документ — английский [README.md](README.md);
> этот перевод может отставать от него. При расхождении верен английский.
> Остальные документы проекта — `docs/SPEC.md`, `docs/DX_GUIDE.md`,
> `docs/MODX_HEADLESS_INSTALL.md` и `docs/adr/` — ведутся только на английском:
> русского перевода у них нет.

Автоматизированное тестовое окружение для дополнений (extras) MODX Revolution 3 — то, чем для Laravel является `orchestra/testbench`.

> **Статус:** реализация завершена. Описанный ниже API соответствует коду в `src/` и сверен с ним исполнением на реальном экстра — см. раздел «FAQ» в [docs/DX_GUIDE.md](https://github.com/modxkit/testbench/blob/main/docs/DX_GUIDE.md) и раздел «Known limitations» в [docs/SPEC.md](https://github.com/modxkit/testbench/blob/main/docs/SPEC.md).

Пакет разворачивает настоящий MODX 3 во временном каталоге, устанавливает его неинтерактивно, загружает в API-режиме и даёт базовые классы тестов с изоляцией состояния. Ни одного ручного шага: подключили в `require-dev` — запустили `composer test`.

## Зачем

В MODX 3 интеграционный слой экстра — xPDO-модели, процессоры, плагины, системные настройки — на практике не тестируется: поднять окружение вручную дорого, а браузерный инсталлятор нельзя запустить в CI. Пакет убирает эту преграду.

## Требования

- PHP 8.2–8.4, расширения `json`, `mbstring`, `pdo`, `pdo_mysql`, `zip` — все объявлены в `composer.json` пакета, отдельно ставить ничего не нужно
- MySQL 8 или MariaDB 10.11 (только для интеграционного уровня)
- MODX Revolution 3.1+ (версия по умолчанию — `3.2.3-pl`). **Линейка 3.0.x не поддерживается:** её ядро не поднимается в API-режиме полноценно — `modX::reloadConfig()` дважды включает один и тот же файл модели и роняет процесс с `Cannot redeclare class`, а до этого `getOption('core_path')` отдаёт `null`. Причина лежит внутри ядра 3.0.5, и пакет её не чинит. Проверяются 3.1.2-pl и 3.2.3-pl
- PHPUnit 10.5 / 11 / 12 — приезжает вместе с пакетом (`require`), отдельно требовать не нужно

## Установка

```bash
composer require --dev modxkit/testbench
```

PHPUnit требовать отдельно не нужно: `ModxKit\Testbench\TestCase` наследует
`PHPUnit\Framework\TestCase`, поэтому PHPUnit объявлен в `require` пакета и приезжает вместе
с ним (проверено резолвингом в чистом проекте: `vendor/bin/phpunit` появляется).

## Быстрый старт

`phpunit.xml`:

```xml
<phpunit bootstrap="vendor/modxkit/testbench/bootstrap.php"
         cacheDirectory=".phpunit.cache"
         beStrictAboutOutputDuringTests="true">
    <testsuites>
        <testsuite name="unit"><directory>tests/Unit</directory></testsuite>
        <testsuite name="integration"><directory>tests/Integration</directory></testsuite>
    </testsuites>
</phpunit>
```

Гоняйте сьюты **разными процессами** (`phpunit --testsuite unit`, затем
`phpunit --testsuite integration`). Голый `vendor/bin/phpunit` без `--testsuite` гонит оба
сьюта в одном процессе PHP, а уровни подключают ядро MODX разными путями: **если пути расходятся**,
пакет отказывается поднимать второе ядро вместо того, чтобы смешать два
(`KernelBootstrapper::assertSingleCorePerProcess()`). Пока пути совпадают, голый прогон зелёный —
измерено, — так что разделение здесь предосторожность, а не отказ, который вы обязательно увидите.
См. раздел «CI».

Интеграционный тест:

```php
use ModxKit\Testbench\Concerns\RefreshesDatabase;
use ModxKit\Testbench\Package\PackageDefinition;
use ModxKit\Testbench\TestCase;
use MyVendor\MyExtra\Model\Job;

final class JobTest extends TestCase
{
    // Обязателен для любого экстра, объявляющего свои таблицы через ->tables():
    // их создание — это DDL, а DDL в MySQL делает неявный commit и рвёт транзакцию теста.
    use RefreshesDatabase;

    protected function packageDefinition(): PackageDefinition
    {
        $core = dirname(__DIR__) . '/';

        return PackageDefinition::make('myextra')
            ->corePath($core)
            ->model('MyVendor\\MyExtra\\Model', $core . 'src/', 'mex_', 'MyVendor\\MyExtra\\')
            ->tables(Job::class)
            ->settings(['myextra_chunk_size' => 500]);
    }

    public function testJobPersists(): void
    {
        $job = $this->modx->newObject(Job::class);
        $job->set('name', 'nightly');

        self::assertTrue($job->save());
        $this->assertObjectExists(Job::class, ['name' => 'nightly']);
    }
}
```

Быстрый тест без базы данных:

```php
use ModxKit\Testbench\Unit\UnitTestCase;

final class PriceFormatterTest extends UnitTestCase
{
    public function testEmitsEvent(): void
    {
        (new PriceFormatter($this->modx))->format(100.0);

        $this->assertEventInvoked('OnMyExtraPriceFormatted');
    }
}
```

## Два уровня

|                           | Уровень 1 — Unit                                           | Уровень 2 — Integration                        |
| ------------------------- | ---------------------------------------------------------- | ---------------------------------------------- |
| Базовый класс             | `ModxKit\Testbench\Unit\UnitTestCase`                      | `ModxKit\Testbench\TestCase`                   |
| Нужна БД                  | нет                                                        | да                                             |
| Нужны файлы ядра на диске | да (классы `modX`/`xPDO` подгружаются по-настоящему)       | да                                             |
| Нужна установка MODX      | нет                                                        | да, выполняется автоматически                  |
| Что проверяет             | бизнес-логику, контракты, работу с настройками и событиями | xPDO-модели, схему, процессоры, плагины, права |

## Изоляция состояния

Каждый тест выполняется внутри транзакции и откатывается. Если тест выполняет DDL или ставит транспортный пакет, транзакция теряется — пакет обнаруживает это и предлагает трейт:

```php
use ModxKit\Testbench\Concerns\RefreshesDatabase;
```

Он восстанавливает базу из baseline-снапшота, снятого сразу после установки ядра.

Детектор потери изоляции ловит четыре способа её потерять: неявный commit после DDL (снятый
флаг `SERVER_STATUS_IN_TRANS`), `START TRANSACTION`/`BEGIN` сырым SQL и `commit()` с новым
`beginTransaction()` (сторожевая метка, пережившая откат), а также таблицы MyISAM (проверка
движка перед тестом).

**Оговорка, которую надо прочитать сразу, а не потом.** Запись, сделанную с ДРУГОГО соединения
или из подпроцесса, детектор не видит и увидеть не может: она транзакции теста не подчинена в
принципе. Для этого случая нужен `RefreshesDatabase`; `TransportInstaller` внутри транзакции
теста отказывается работать сам.

Кроме базы после каждого теста возвращаются файловый кеш ядра `core/cache/` (кроме `logs/`) и
сессионные переменные MySQL; `$modx->error` сбрасывается перед каждым тестом. А вот
`$modx->services`, `$xpdo->packages` и файлы, установленные транспортным пакетом, живут до
конца процесса PHPUnit — исчерпывающий список в `docs/DX_GUIDE.md`, раздел 4.

## Имена

Пакет называется `modxkit/testbench`, PHP-namespace — `ModxKit\Testbench\`. Несколько имён вокруг
него пишутся не как `modxkit/testbench`:

- `vendor/bin/modx-testbench` — консольный бинарь; `vendor/bin/testbench` не существует
- `MODX_TESTBENCH_…` — префикс всех переменных первой колонки таблицы ниже
- `modx-testbench` — сегмент, который присутствует в путях кеша и окружения по умолчанию; строки
  `MODX_TESTBENCH_CACHE_DIR` и `MODX_TESTBENCH_WORKSPACE` той же таблицы приводят эти умолчания
- `modx_testbench` — имя базы по умолчанию (`MODX_TESTBENCH_DB_NAME`)
- `modx-testbench: ` — начало некоторых собственных сообщений пакета, например
  `modx-testbench: the Composer autoloader was not found …`

Это два разных сорта имени, и они не взаимозаменяемы. `modxkit/testbench` — АДРЕС: его кто-то
разрешает — Composer в `require`, каталог внутри `vendor/`, `uses:` переиспользуемого workflow.
(`ModxKit\Testbench\` — тоже адрес, в том написании, которое разрешает автозагрузчик.) Первые
четыре имени из списка — другого сорта: по ним находят — исполняемый файл по имени, переменные в
окружении, базу и каталоги на диске. Что определяют значения этих переменных — предмет раздела
«Что именно приводит к переустановке» ниже.

### Что именно приводит к переустановке

Каталог окружения адресуется отпечатком конфигурации — хешем от всех переменных, которые
определяют результат установки: провайдера и его собственных параметров (версия релиза для
`zip`, ветка для `git`, путь к дистрибутиву для `local`), всех `MODX_TESTBENCH_DB_*` (включая
пользователя, пароль и сортировку) и всех `MODX_TESTBENCH_ADMIN_*`. Меняете любую из них —
получаете другое окружение, установленное заново; окружение, поставленное с прежними
значениями, остаётся на месте и переиспользуется, если вы вернёте их обратно.

Параметры, установку не определяющие, отпечаток не меняют: `MODX_TESTBENCH_CACHE_DIR`,
`MODX_TESTBENCH_WORKSPACE`, `MODX_TESTBENCH_FORCE_INSTALL`, а также параметры того провайдера,
который сейчас не выбран (`MODX_TESTBENCH_GIT_REF` при `provider=zip` и наоборот).

> **Обновление с версии пакета до этой.** Изменился и состав отпечатка, и сам каталог, в
> котором пакет держит окружения (см. следующий раздел), поэтому первый прогон после
> обновления адресует ДРУГОЙ каталог и ставит окружение заново. Прежний каталог
> (`sys_get_temp_dir()/modx-testbench/<старый хеш>`) не удаляется: пакет о его имени уже не
> знает. Он безвреден, но занимает место — удалить сирот прежней раскладки можно так:
>
> ```bash
> find "$(php -r 'echo sys_get_temp_dir();')/modx-testbench" \
>      -mindepth 1 -maxdepth 1 -type d ! -name workspaces -exec rm -rf {} +
> ```
>
> Исключение `! -name workspaces` обязательно, и это не перестраховка: если ни `HOME`, ни
> `XDG_CACHE_HOME` не заданы, ЖИВОЕ окружение лежит как раз в
> `<временный каталог>/modx-testbench/workspaces/<хеш>` — то есть внутри удаляемого. Без
> исключения команда сносила бы рабочее окружение ровно у той аудитории, о которой разделом
> выше сказано, что она в общий временный каталог и попадает. Тех, кто задаёт
> `MODX_TESTBENCH_WORKSPACE`, всё это не касается: путь не меняется, и каталог
> переиспользуется обычной переустановкой.

### Каталог окружения лежит в приватном каталоге пользователя

Имя каталога окружения — отпечаток конфигурации, а в него захеширован пароль СУБД и пароль
администратора (это требование FR-ENV-4: окружение, поставленное с другими учётными данными,
переиспользовать нельзя). Пока такое имя лежало в общем временном каталоге системы, его мог
прочитать любой пользователь машины — а зная остальные слагаемые отпечатка (хост, порт, имя
базы, версию MODX), по нему можно офлайн перебирать слабый пароль. Поэтому каталог окружения
живёт в `$XDG_CACHE_HOME` (иначе `$HOME/.cache`), рядом с кешем релизов, в собственном
подкаталоге `workspaces/`. Весь этот отрезок пути пакет создаёт сам и сразу с правами `0700` —
и подкаталог `workspaces/` тут несущий, а не декоративный: каталог `modx-testbench` общий с
кешем релизов и вполне может уже существовать с широкими правами.

Если не заданы ни `HOME`, ни `XDG_CACHE_HOME` — так бывает в контейнере, запущенном с
`--user`, или в cron с пустым окружением, — пакету деваться некуда, и он возвращается в общий
временный каталог системы. Утечки имени это само по себе не создаёт: отрезок пути и там
создаётся с правами `0700`, и посторонний получает `Permission denied` уже на `modx-testbench`
(измерено в контейнере Linux, где `/tmp` имеет права `1777`).

А вот если каталог `.../modx-testbench/workspaces` **уже существовал** и открыт посторонним на
чтение и проход — например, его заранее создал кто-то другой в общем `/tmp`, — имя каталога
окружения действительно читается, и пакет об этом говорит: печатает предупреждение
(`E_USER_WARNING`) и повторяет его голосом `bin/modx-testbench install`, потому что видимость
предупреждений PHP зависит от ini. Чужие права пакет при этом не правит — это не его каталог.
Лечится `chmod 700` на названном каталоге либо `MODX_TESTBENCH_WORKSPACE` с последующей
переустановкой окружения.

### После обновления пакета окружение переустанавливается один раз

В `testbench.lock.json` записана ревизия установочного поведения. Если обновление пакета
изменило то, что установка кладёт в базу или в файл снимка, ревизия увеличивается, и первый
же `install` (или первый прогон тестов) разворачивает окружение заново — мигрировать старое
на месте нечем. Выглядит это как десяток-другой секунд паузы на ровном месте; это ожидаемо и
происходит однократно. **Прерывать её не нужно** — впрочем, и не опасно: каталог помечен
файлом `.testbench-workspace` на всё время уборки, и прерванная переустановка доводится
следующим запуском.

### Baseline снимается и читается одной и той же стратегией

Снимок базы делает либо клиент `mysqldump` (переносит и представления, и триггеры), либо
встроенный PHP-фолбэк — что доступно, тем и снимается. Клиенты ищутся парами и в таком
порядке: сперва `mysqldump`/`mysql`, затем `mariadb-dump`/`mariadb` (под вторыми именами
клиенты MariaDB лежат начиная примерно с 12.x, где старых симлинков уже нет). Чем в итоге
снят снимок, `bin/modx-testbench install` печатает отдельной строкой — откат на PHP-фолбэк
раньше происходил молча. Чем именно, пакет записывает в
`testbench.lock.json` и по этой записи выбирает, чем снимок читать: форматы не
взаимозаменяемы, и дамп `mysqldump`, отданный PHP-фолбэку, спотыкается о клиентскую команду
`DELIMITER` уже после того, как база вычищена под восстановление.

Поэтому если baseline снят `mysqldump`, а клиентов в `PATH` в этом запуске нет (частый случай:
терминал, IDE и `make` видят разный `PATH`), пакет откажет — не тронув базу — и предложит либо
вернуть клиенты в `PATH`, либо пересоздать окружение. Окружения, развёрнутые предыдущей
версией пакета, этой записи не несут, поэтому переустанавливаются один раз (см. раздел выше):
угадать происхождение уже лежащего на диске снимка нечем, а цена ошибки — снесённая база.

### Что изменилось в публичных интерфейсах

Правок, помеченных «внутренний слой», касается только тот, кто расширяет пакет своими
классами; остальные видны из тестов потребителя.

- **Внутренний слой.** `ModxKit\Testbench\Database\Dumper` получил метод `format(): string` — имя формата снимка,
  которое установка пишет в `testbench.lock.json` (`php`, `mysql` или ваше собственное).
  Сторонняя реализация интерфейса без него не скомпилируется.
- **Внутренний слой.** `ModxKit\Testbench\Environment\LockFile::__construct()` получил параметр `$snapshotFormat`
  ВОСЬМЫМ, перед `$installRevision` (тот стал девятым). Именованные вызовы — единственный вид
  в самом пакете — не затронуты, вызов с семью позиционными аргументами тоже. Ломается вызов
  с ВОСЬМЫМ позиционным аргументом, которым раньше была ревизия установки, и ломается
  по-разному: под `declare(strict_types=1)` — сразу `TypeError`, без него хуже — `int`
  молча приводится к строке, ревизия оказывается в поле формата, а сама ревизия берётся из
  умолчания. Проверено исполнением обоих случаев.
- Стратегия `mysqldump` больше не кладёт `init-command` в группу `[client]` временного файла
  опций. Прежнее размещение убивало снятие снимка отказом ещё до соединения с СУБД, то есть
  `modx-testbench install` не проходил вовсе. Измерено на пяти сборках клиента: отказывали
  `mariadb-dump` 10.6.28, 10.11.18 и 12.3.2 и `mysqldump` 8.0.46, принимал только `mysqldump`
  8.4.11. Про неизмеренные сборки этих линеек пакет ничего не утверждает. Отказ бьёт по обеим
  линейкам сразу: под именами `mysql`/`mysqldump` лежат и клиенты MariaDB
  (`default-mysql-client` Debian), и клиенты Oracle (`mysql-client` Ubuntu). Сообщение при
  этом различается по вендору: Oracle печатает `mysqldump: [ERROR] unknown variable
  'init-command=…'.`, MariaDB — `mysqldump: unknown variable 'init-command=…'`, без префикса
  и точки. На раннерах GitHub Actions ставится именно клиент Oracle — измерено на образе
  `ubuntu:24.04`, где `apt-get install mysql-client` даёт
  `mysqldump Ver 8.0.46-0ubuntu0.24.04.4`, — и именно на нём до этой починки падало снятие
  снимка в CI. Теперь опция лежит в группе `[mysql]`, и
  ограничение ожидания metadata lock (30 секунд вместо серверного умолчания в год) получают
  чистка базы и восстановление снимка. СНЯТИЕ снимка идёт с серверным умолчанием: если вы
  снимаете baseline клиентом Oracle 8.4+ и рассчитывали на ограничение во время снятия — его
  больше нет. Подробности и измерения — FR-ISO-5b в `docs/SPEC.md`.
- `ModxKit\Testbench\Database\PhpDumper::load()` (то есть восстановление на любой машине без
  клиентов `mysql`) теперь удаляет из базы ПРЕДСТАВЛЕНИЯ — и созданные после снятия baseline,
  и существовавшие до него. Так требует контракт `Dumper`: восстановление возвращает базу
  ровно к содержимому снимка, а снимок php-стратегии представлений не несёт и вернуть их не
  может. Если ваши тесты полагаются на представление, живущее в тестовой базе, — создавайте
  его в самом тесте (`setUp()`) либо ставьте клиенты `mysql`/`mysqldump`, чтобы baseline
  снимался стратегией, которая представления переносит.
- Уровень 1 (`ModxKit\Testbench\Unit\UnitTestCase`) больше не игнорирует критерий, который не
  является массивом. Скаляр означает первичный ключ `id` — так его понимает и ядро
  (`xPDO::sanitizePKCriteria()`); `getObject()` вовсе без критерия возвращает `null`; объект
  запроса (`xPDOQuery`, `xPDOCriteria`) заглушка отклоняет `UnsupportedStubOperationException`,
  а не ищет молча «без критериев». Тест, который полагался на прежнее поведение — заглушка
  отдавала первый попавшийся засеянный объект на любой скаляр, — покраснеет; это и есть цель
  правки. Модель с первичным ключом не `id` адресуйте явным массивом.
- Процессоры ушли с уровня 1. `$modx->runProcessor()` на заглушке отказывает
  `UnsupportedStubOperationException` вместо прежнего правдоподобного `success => false`
  с сообщением `Requested processor not found`. Тест уровня 1, «проверявший» отказ
  процессора, был вакуумным — процессор не исполнялся ни разу; перенесите его на
  `ModxKit\Testbench\TestCase`. Строка `docs/SPEC.md` про область уровня 1 исправлена под это.
- Хранилище засеянных объектов (`seed()`) стало видеть закрытые поля дубля — раньше
  критерий по такому полю не совпадал никогда, — а `null` в критерии совпадает теперь только
  с `null` (было: `['field' => null]` находил объект с хранимым `0`, `''` или `false`).
  Дубль, чей `toArray()` вернул не массив, отказывает исключением пакета вместо `TypeError`
  из его внутренностей.
- `$modx->invokeEvent()` на уровне 1 возвращает `false`, а не пустой массив: пустой массив в
  ядре означает «событие есть, плагины отработали и промолчали», а у заглушки карты событий
  нет вовсе. Тест, писавший `foreach ($this->modx->invokeEvent(...) as ...)`, покраснеет;
  факт вызова проверяйте `assertEventInvoked()`.
- `$modx->getOption()` на уровне 1 стал портом `xPDO::getOption()`: читает `$modx->config`
  (раньше — собственный массив, и правка `$modx->config` была не видна), понимает `$skipEmpty`
  и массив ключей. Прежнее поведение отличалось на пустых строках и на массиве ключей
  (`Array to string conversion`).
- `new TestbenchModx(...)` отказывает `UnsupportedStubOperationException`. Заглушка и раньше
  создавалась только через `TestbenchModx::create()`; конструктор, доставшийся от `modX`,
  давал объект, каждый метод которого падал `Error`'ом на неинициализированном свойстве.
- Состав зависимостей пакета изменился: `phpunit/phpunit` переехал из `require-dev` в
  `require` (публичный API пакета наследует `PHPUnit\Framework\TestCase`, без PHPUnit он не
  грузится вовсе), а к объявленным расширениям добавились `ext-pdo_mysql` (DSN пакета всегда
  `mysql:`) и `ext-mbstring`. Требовать PHPUnit отдельно больше не нужно; вреда от явного
  требования нет. Отсутствие драйвера теперь ловится резолвингом, а не `PDOException: could
  not find driver` в середине прогона.
- `ModxKit\Testbench\Concerns\InteractsWithModx::runProcessor()` получил третий параметр
  `array $options = []` — он уходит в `modX::runProcessor()` как есть, ради
  `$options['processors_path']`. Со всеми существующими вызовами совместимо; переопределение
  метода в своём базовом классе тестов нужно расширить той же сигнатурой. Без этого пути
  процессор экстра, адресованный строкой, не находился никогда, а ответ выглядел как обычный
  отказ процессора.
- `InteractsWithModx::createUser()` получил второй параметр `array $profile = []` — поля
  `modUserProfile` (`email`, `fullname`). Раньше такие поля, переданные в первом аргументе,
  молча исчезали: `modUser::fromArray()` игнорирует неизвестные ему поля, и профиль получал
  сгенерированный адрес.
- `ModxKit\Testbench\TestCase` получил точку расширения `afterPackageRegistered()` — она
  вызывается из `setUp()` сразу после применения `PackageDefinition`, внутри уже открытой
  изоляции. Если в вашем базовом классе тестов уже есть метод с таким именем, он станет
  переопределением хука и начнёт вызываться сам.
- `PackageDefinition::make('')` теперь отказывает вместо создания описания с пустым
  `modNamespace`, регистрация которого выглядела успешной, не давая ядру ни одного пути экстра.
- `Env::int()` (`MODX_TESTBENCH_DB_PORT` и другие числовые переменные) отвергает нечисловое
  значение вместо молчаливого усечения: `330a` больше не превращается в `330`.
- `ModxKit\Testbench\Support\CoreAutoloader::register()`, вызванный ВТОРОЙ раз с ДРУГИМ путём
  к ядру, теперь бросает `TestbenchException` вместо тихого no-op'а. Раньше вызывающий получал
  «успех», а в процессе оставалось ядро из первого каталога — тест работал с одним
  дистрибутивом, полагая, что работает с другим (два дистрибутива в одном процессе PHP
  несовместимы в принципе: одноимённые классы ядра и коллизия `ComposerAutoloaderInit…`).
  Повторный вызов с тем же путём (в том числе с хвостовым слешем) остаётся no-op'ом. Если
  ваши тесты сознательно переключают `MODX_TESTBENCH_CORE_PATH` между дистрибутивами,
  разводите их по процессам (`#[RunInSeparateProcess]`).
- Манифест установки `setup/config.xml` удаляется после УСПЕШНОЙ установки, а
  `core/config/config.inc.php` получает права `0600`: оба файла несут пароли открытым
  текстом, а рабочий каталог по умолчанию лежит в общем `/tmp`. На отказе манифест остаётся —
  это главный диагностический артефакт, на который ссылается текст исключения. Скрипт,
  читавший `setup/config.xml` рабочего каталога после установки, файла больше не найдёт.
  Ужесточение прав — мера защиты, а не критерий успеха: если `chmod` не проходит, установка
  не отменяется. Речь ровно о случае «файл записался, а сузить права не вышло»: так, по
  общему описанию, ведут себя часть сетевых и контейнерных монтирований — сами мы этого не
  измеряли. Измеренные на macOS отказы `chmod` — файл с флагом неизменяемости
  (`chflags uchg`) и том, смонтированный только для чтения — сюда не попадают: на них
  отказывает и запись, то есть установка падает раньше. А образ FAT32, вопреки ходовому
  объяснению «том без POSIX-прав», `chmod` не отвергает вовсе — возвращает `true`, том
  смонтирован с `noowners`, и режим остаётся 0700. Не отвергает и ACL `deny writesecurity`
  на владельце.

  О том, что файл с паролем доступен не только владельцу, `bin/modx-testbench install`
  сообщает отдельным предупреждением, оставляя код выхода успешным. Проверка живая, а не
  память об установке, поэтому она честна и на повторном запуске по уже готовому окружению;
  тот же список отдаёт новый метод
  `ModxKit\Testbench\Environment\Workspace::exposedSecretFiles()`. Есть и второй канал —
  `E_USER_WARNING` из `ModxKit\Testbench\Support\FilePermissions`, — но он зависит от ini
  (при `display_errors=0` вместе с `log_errors=0` не доходит никуда), поэтому единственным
  его не оставили. Третий: `bin/modx-testbench status` печатает тот же живой ответ отдельной
  строкой `Password exposure` — либо список файлов, либо `none — the environment files and the
  directory name are private to you`.

  И четвёртый, для пути, на котором не зовут ни одной команды, — собственного
  `vendor/bin/phpunit` потребителя: opt-in расширение PHPUnit
  `ModxKit\Testbench\PHPUnit\ExposureWarningExtension`. Регистрируется одной строкой `phpunit.xml`:

```xml
<extensions>
    <bootstrap class="ModxKit\Testbench\PHPUnit\ExposureWarningExtension"/>
</extensions>
```

  Оно пишет предупреждение в STDERR один раз за прогон, до первого теста, и молчит, когда
  экспозиции нет. Opt-in — намеренно: тот, кто не хочет ни слова из своего прогона, строку не
  добавляет. `bootstrap.php`, который на этом же пути и готовит окружение, МОЛЧИТ — почему,
  сказано ниже.

  Каталог окружения по умолчанию создаётся с правами `0700`, и это снимает большую часть
  вопроса: без права на вход в каталог режим лежащего внутри файла роли не играет (измерено
  на `debian:stable` — чужой пользователь получает `Permission denied` и на чтение файла
  `0644`, и на листинг каталога `0700`). Остаётся каталог, заданный вручную через
  `MODX_TESTBENCH_WORKSPACE`: там права выбирает потребитель, и они значат ровно то же, что и
  раньше.

  Ещё одним каналом мог бы стать `bootstrap.php` — именно он готовит окружение на первом
  `vendor/bin/phpunit`, и дыра «окружение подготовил бутстрап, `install` никто не звал»
  закрывается только там. Он о незащищённых файлах МОЛЧИТ, и это решение, а не упущение.
  Печать без разбора ломает тесты, идущие в отдельном процессе, — PHPUnit считает непустой
  STDERR дочернего процесса ошибкой; измерено: на правах `0644` и `fwrite(STDERR, …)`, и
  `trigger_error(…, E_USER_WARNING)` превращают восемь тестов с `#[RunInSeparateProcess]` в
  ошибки. Работающее условие при этом существует (`ob_get_level() === 0` — измерено:
  предупреждение доходит, прогон зелёный), но отказывает оно МОЛЧА: бутстрап потребителя,
  начинающийся с `ob_start()`, гасит предупреждение без следа. Разбор целиком — комментарий в
  конце `bootstrap.php`.

### `MODX_TESTBENCH_WORKSPACE` — каталог удаляется целиком

Пакет владеет каталогом окружения безраздельно: при переустановке (несовпадение отпечатка,
`--force`, `MODX_TESTBENCH_FORCE_INSTALL=1`) и по команде `destroy` он удаляется рекурсивно.

Чтобы опечатка вида `MODX_TESTBENCH_WORKSPACE=$PWD` не стоила вам рабочего каталога, удаление
разрешено только для каталогов, которые создал сам пакет: пустых, либо помеченных файлом
`.testbench-workspace`, либо содержащих `testbench.lock.json`. Любой другой непустой каталог
даёт отказ с ненулевым кодом выхода и остаётся нетронутым.

Указывайте в этой переменной отдельный каталог — несуществующий или пустой.

Пакет резервирует ещё один путь — **соседний** `<workspace>.new`. Сменное ядро сначала доставляется
туда и занимает место текущего окружения только после успешной доставки, поэтому прерванная
переустановка не оставляет недописанного окружения. Тот же страж владения распространяется и на
него: `<workspace>.new`, созданный не пакетом, не удаляется — команда отказывает с
`WorkspaceOwnershipException`, содержимое остаётся на месте, а в сообщении назван путь, которого
вы не задавали. Держите это соседнее имя свободным.

## CLI

```bash
vendor/bin/modx-testbench install [--force]   # развернуть окружение (--force: снести и поставить заново)
vendor/bin/modx-testbench status              # где окружение, какая версия, есть ли снапшот, цела ли БД, открыт ли пароль
vendor/bin/modx-testbench snapshot [capture]  # снять baseline (действие по умолчанию)
vendor/bin/modx-testbench snapshot restore    # восстановить baseline
vendor/bin/modx-testbench destroy [--force]   # удалить окружение
```

`destroy` спрашивает подтверждение. Без TTY (в CI, в скрипте) вопрос не задаётся, а ответом
считается «нет» — в неинтерактивной среде передавайте `--force` явно, иначе команда завершится
успехом, ничего не удалив.

`destroy` удаляет каталог, а не базу: измерено на реальном экстра — в тестовой базе было 70 таблиц
до команды и те же 70 после, при том что каталог окружения исчез. Нужна пустая база — удаляйте её
сами.

Если убрать удалось не всё (нет прав на часть дерева, занятый файл), `destroy` возвращает `1` и
говорит об этом: каталог при этом остаётся помеченным как принадлежащий пакету, поэтому
повторный запуск попробует доубрать его.

`destroy` без переменных адресует окружение ТЕКУЩЕЙ конфигурации. Окружения, поставленные с
другими значениями (другая версия MODX, другая СУБД, другие учётные данные), лежат в соседних
каталогах с другими отпечатками, и их именами пакет уже не располагает. Такое окружение
удаляется той же командой, если адресовать каталог явно:

```bash
MODX_TESTBENCH_WORKSPACE=~/.cache/modx-testbench/workspaces/<отпечаток> \
  vendor/bin/modx-testbench destroy --force
```

Это не `rm -rf`: команда сверяет принадлежность каталога пакету (лок или метка) и на чужой
каталог отвечает отказом, а не сносом. Рецепт `find` выше — про ДРУГОЕ: он убирает сирот
прежней раскладки, лежавших мимо `workspaces/`, и внутрь `workspaces/` намеренно не заходит.

Строка `Database` показывает, сколько таблиц с префиксом в базе сейчас и сколько их было при
установке (`70/70 tables`). Расхождение означает, что окружение повреждено: `install`
починит его из baseline либо переустановит.

Пароль СУБД в выводе всех команд заменяется на `***`; пустой пароль показывается как `empty`.

## CI

```yaml
jobs:
  testbench:
    uses: modxkit/testbench/.github/workflows/testbench.yml@v1
    with:
      php-versions: '["8.2","8.3","8.4"]'
      modx-versions: '["3.1.2-pl","3.2.3-pl"]'
      working-directory: core/components/myextra
```

Workflow запускает у вас `composer test`, поэтому эти скрипты **обязаны** быть в вашем
`composer.json` — без них джоба падает на `Command "test" is not defined`:

```json
"scripts": {
    "test": ["@test:unit", "@test:integration"],
    "test:unit": "phpunit --testsuite unit",
    "test:integration": "phpunit --testsuite integration"
}
```

**Если в вашем `composer.json` ключ `test` уже есть, этот блок его замещает, и ваш собственный сьют
молча исчезает из CI** — workflow запускает ровно `composer test` и получает только два сьюта выше.
Измерено на экстра, чей сьют содержит 1879 тестов: после дословного копирования блока `composer test`
прогнал 4. Оставьте свою точку входа и составьте из них, назвав тот сьют, который у вас уже есть:

```json
"scripts": {
    "test": ["@test:default", "@test:unit", "@test:integration"],
    "test:default": "phpunit --testsuite default",
    "test:unit": "phpunit --testsuite unit",
    "test:integration": "phpunit --testsuite integration"
}
```

Здесь `default` — имя вашего существующего сьюта в `phpunit.xml`, каким бы оно ни было; `test:default`
— имя на ваш выбор, пакет его не знает и не требует.

Два процесса вместо одного `vendor/bin/phpunit` — не украшение: уровень 1 и уровень 2
подключают ядро MODX разными путями, и в одном процессе это возвращало фатал
`Cannot redeclare class ComposerAutoloaderInit…`. Подробности — в
[docs/DX_GUIDE.md](https://github.com/modxkit/testbench/blob/main/docs/DX_GUIDE.md), раздел «Wiring up CI».

## Ограничения

- Одна версия ядра на процесс PHPUnit — матрица версий MODX разводится по джобам CI.
- Пакет заводит в тестовой базе служебную таблицу `testbench_isolation_guard` (сторожевая
  метка детектора потери изоляции): учётной записи нужно право `CREATE TABLE`, а не только
  `CREATE` на базу. Префикса ядра у неё нет намеренно — см. `docs/DX_GUIDE.md`, раздел 4.
- Только MySQL/MariaDB: инсталлятор MODX 3 фактически завязан на MySQL ([ADR-0002](https://github.com/modxkit/testbench/blob/main/docs/adr/0002-no-in-memory-sqlite.md)).
- Таблицы MyISAM и DDL не откатываются транзакцией — используйте `RefreshesDatabase`; детектор называет обе причины до того, как тест поверит откату.
- Экстра, объявляющий свои таблицы через `PackageDefinition::tables()`, тестируется **только**
  под `RefreshesDatabase`: их создание — DDL, а DDL рвёт транзакцию теста.
- Первая установка занимает десятки секунд; дальше окружение переиспользуется.
- Провайдер `local` отказывается копировать дистрибутив, если внутри есть символическая ссылка
  на каталог: `RecursiveIteratorIterator` внутрь неё не спускается, и ссылка молча приехала бы
  пустым каталогом. Замените ссылку реальным каталогом.
- Пакет создаёт тестовую БД сам, если её нет: CLI-инсталлятор MODX 3, не найдя базы, не может
  прочитать версию сервера и записывает в `core/config/config.inc.php`
  `'override_table' => 'MyISAM'` — все 70 таблиц ядра создавались бы MyISAM, а MyISAM транзакций
  не поддерживает. После установки пакет проверяет движки таблиц и отказывает, если среди них
  есть нетранзакционные. Требование к учётной записи — право `CREATE`.
- Файлы, установленные транспортным пакетом (`core/components/`, `assets/components/`,
  `core/packages/`), снапшотом не откатываются: он возвращает базу, но не диск. См.
  [docs/DX_GUIDE.md](https://github.com/modxkit/testbench/blob/main/docs/DX_GUIDE.md), раздел 4, «What is rolled back and what is not».
- **Известная незакрытая дыра: на основном пути потребителя об открытом пароле не сообщает
  никто сам по себе.** `bootstrap.php` готовит окружение на первом `vendor/bin/phpunit`, и если
  `chmod` не прошёл, файлы с паролем от базы остаются доступны не только владельцу — а
  `bootstrap.php` намеренно молчит (печать оттуда превращает каждый тест
  `#[RunInSeparateProcess]` в ошибку; полный разбор — в комментарии в конце этого файла).
  Предупреждение есть у `install`, у `status`, у `Workspace::exposedSecretFiles()` и у opt-in
  расширения `ExposureWarningExtension` — каждое из них надо позвать. Что сужает дыру, измерено:
  штатная установка создаёт каталог с режимом `0700`, а `core/config/config.inc.php` — с `0600`,
  на нормально установленном окружении `exposedSecretFiles()` возвращает пустой список, и пароль
  лежит ровно в одном этом файле. Форму отказа `chmod`, ради которой дыра оставлена, воспроизвести
  не удалось — см. раздел про `install` выше.

## Разработка самого пакета

`composer qa` — cs-fixer, Rector, PHPStan и оба сьюта. Стадия Rector объявлена как
`rector process --dry-run --clear-cache`, и сбрасывать кеш обязательно: инкрементальный
`rector:check` пересканирует только изменённые файлы, из-за чего в этом проекте зелёный
результат трижды подряд скрывал настоящую регрессию.

Задачи, которые трогают статическое состояние процесса, обязаны прогоняться ещё и с
`--order-by=random` и `--order-by=reverse`: зависимость от порядка тестов возникала в проекте
трижды.

**Чего интеграционный сьют требует от учётной записи СУБД.** Потребителю пакета нужен только
`CREATE` на тестовую базу (FR-INSTALL-5). Собственному сьюту пакета нужно больше: временную
учётную запись с урезанными правами заводят `DatabaseCleanerTest` и `PhpDumperTest` (отказ
сервера посреди уборки и посреди чистки перед восстановлением иначе не воспроизвести, не
трогая глобальных настроек общего сервера) — им нужны глобальные `CREATE USER` и `GRANT`.
`FixtureDatabaseUserTest`, который проверяет саму эту фикстуру, по умолчанию в `composer test`
вообще не собирается (группа `mysql-user-table`, см. ниже) — право `SELECT` на `mysql.user`
для зелёного `composer test` НЕ обязательно.

Это право всё же важно для ДВУХ ДРУГИХ классов: `createFixtureUser()`
(`tests/Support/FixtureDatabaseUser.php`), которым пользуются и `DatabaseCleanerTest`, и
`PhpDumperTest`, перед созданием СВОЕЙ учётки сметает чужие сироты через
`dropStaleFixtureUsers()` — она читает `mysql.user` и ГЛОТАЕТ `PDOException` молча. Без этого
права сьют остаётся зелёным (отказ уборки не всплывает наружу), но сметание не срабатывает и
осиротевшие учётки накапливаются на сервере. Root контейнера из `ci/docker-compose.yml` имеет
и `CREATE USER`/`GRANT`, и это право.

Имена таких учёток начинаются с `modx_tb_`, они удаляются в `tearDown()`, а оставшиеся от
убитого прогона сносятся при следующем создании фикстуры того же класса — если у текущей
учётной записи есть право на `mysql.user`.

**Служебные базы собственного сьюта.** Шесть интеграционных классов держат отдельную базу под
свои проверки; её имя вычисляется из отпечатка окружения и pid прогона
(`ModxKit\Testbench\Tests\Support\RunScopedDatabaseName`), а не захардкожено — иначе два прогона
на одном сервере СУБД сносили бы базы друг у друга посреди чужого теста (найдено живьём тремя
ревьюерами независимо). База, оставшаяся от прогона, убитого по Ctrl-C или таймауту CI,
автоматически не подчищается (в отличие от учёток-фикстур выше, у которых есть сборщик сирот
по префиксу) — снимается вручную `DROP DATABASE`, но ТОЛЬКО по точной ФОРМЕ имени
`<base>_<12 hex>_<pid>` (например, `modx_testbench_snapshot_test_4170f4b0fbac_51234`), НЕ по
общему префиксу `modx_testbench_`: под этот префикс попадают и рабочие базы других
одновременно живущих прогонов той же ветки — измерено на сервере разработки этой ветки, все
12 баз под префиксом (`modx_testbench_t26`, `_v26`, `_r1`..`_r4`, `_t23`..`_v25`) НЕ сироты, и
снос по общему префиксу уничтожил бы их тоже.

**`failOnSkipped` и группы, зависящие от окружения.** Сьют не допускает штатных пропусков:
`SnapshotFormatTest` (нужны настоящие клиенты `mysqldump`/`mysql` в PATH) и
`FixtureDatabaseUserTest` (нужно право `SELECT` на `mysql.user`) не пропускаются условно, а
исключены группами `mysql-client-tools` и `mysql-user-table` в `phpunit.xml` (рядом с
`mariadb-client`, заведённой раньше для тестов на настоящих клиентах MariaDB). По умолчанию
(`composer test:integration`) все три группы исключены — так остаётся зелёным окружение без
клиентов и без нужной привилегии. Там, где и то, и другое обеспечено штатными шагами самой
джобы (CI — `.github/workflows/tests.yml` ставит клиенты явным шагом и подключается `root`),
запускается `composer test:integration:with-clients`: тот же сьют с ключом
`exclude-group mariadb-client` вместо списка исключений `phpunit.xml` — включает обе группы,
зависящие от окружения, а не от docker; сам docker для `mariadb-client` по-прежнему не
поднимается. Джоба, где клиенты стоят только под именами `mariadb`/`mariadb-dump`, запускает обычный
`composer test:integration`: группе `mysql-client-tools` нужна пара имён `mysqldump`/`mysql`,
и там она должна оставаться снаружи вместе с остальными. Подробности и предостережение о
хрупкости этой конструкции — комментарий в `phpunit.xml`.
